Bonnes Pratiques R

Un guide pratique pour produire du code R de qualité : propre, optimisé, et livré sous la bonne forme. Ces bonnes pratiques vous aideront à maintenir, partager et faire évoluer vos développements avec confiance.

Partie 1 : Coder proprement en R

La qualité d'un code va au-delà de son simple bon fonctionnement. Un code propre est maintenable, clair et limpide — il peut être lu et amélioré par n'importe quel développeur, pas seulement son auteur.

« La logique doit être simple, pour que les bogues aient du mal à se cacher. Un code propre fait une chose et le fait bien. »
— B. Stroustrup, inventeur du C++

Un code propre doit être explicite, lisible, simple, parcimonieux, non redondant et harmonieux.

Les règles de propreté en R

Ces principes généraux se déclinent en règles concrètes appliquées au langage R.

Indentation

L'indentation n'affecte pas l'exécution en R, mais un script mal indenté perd significativement en lisibilité. Elle révèle aussi les parties trop imbriquées qui bénéficieraient d'une réécriture.

Commentaires

N'écrire des commentaires que s'ils sont irremplaçables. Un code propre n'en a pas besoin. Le bon commentaire est celui qui ne peut pas être remplacé par du code lui-même plus explicite.

Le pipe natif |>

Préférer le pipe natif |> au %>% de 'magrittr'. Il est plus rapide, évite une dépendance, et permet de construire des pipelines de transformations lisibles.

Gestion des paquets

Minimiser les dépendances. Signaler les imports avec paquet::methode. Pour les paquets où seule une ou deux fonctions sont utilisées, chercher des alternatives natives de R.

Lecture / écriture

Vérifier l'existence des fichiers avec base::file.exists() avant toute lecture. Construire les chemins avec base::file.path() pour la lisibilité et la portabilité.

Pas de codage dynamique

Ne jamais utiliser eval(), parse(), get() ou assign(). Ces fonctions rendent le débogage laborieux. Dans 99 % des cas, ce n'est pas nécessaire.

Référencement des colonnes

Préférer Table[["colonne"]] au symbole dollar Table$colonne. L'opérateur $ fait de l'auto-complétion implicite et peut retourner une colonne inattendue.

Gestion des fonctions

Trois règles essentielles gouvernent l'écriture de fonctions de qualité :

  1. Une fonction ne fait qu'une seule chose, et le fait bien. Son nom doit l'énoncer clairement. Pas d'effets de bord, pas d'arguments booléens indicateurs. Des tests unitaires vérifient son bon fonctionnement.
  2. Écrire des fonctions courtes. À chaque passe d'écriture, considérer qu'elle est trop longue et essayer de la raccourcir. Le seuil maximal usuel est de 30 à 50 lignes.
  3. Limiter drastiquement le nombre d'arguments (idéalement ≤ 3). Utiliser des variables locales pour les paramètres constants, des listes pour regrouper les paramètres liés.

L'écriture de fonctions est un processus itératif. La première version n'est jamais la version finale.

Partie 2 : Optimisation du code

L'optimisation est l'étape logique qui suit la réécriture d'un code propre. Elle vise à mobiliser les ressources (RAM et CPU) de manière efficiente et à diminuer le temps d'exécution.

Commencez par identifier les goulots d'étranglement avec profvis::profvis(). En général, moins de 20 % du code est responsable de plus de 80 % du temps d'exécution — loi de Pareto. Mesurez ensuite précisément les blocs critiques avec microbenchmark::microbenchmark().

L'optimisation ne doit jamais se faire au détriment de la propreté du code.

4 leviers d'optimisation

Une fois les goulots d'étranglement identifiés, voici les principales techniques pour améliorer les performances.

Affiner la lecture des inputs

Éviter de charger la totalité d'une table en mémoire. Filtrer colonnes et lignes dès la lecture via col_names, skip, n_max. Pour les bases SQL, optimiser la requête en amont.

data.table

Pour les volumes importants, le package data.table offre des performances bien supérieures aux approches classiques. Sa syntaxe minimise la copie en mémoire et exploite au mieux le processeur.

Vectorisation

Préférer les fonctions vectorisées aux boucles for. Les fonctions de la famille base::apply, base::rbind() ou plyr::join() sont plus rapides et évitent un niveau d'indentation.

Parallélisation

Exploiter toute la puissance des ressources disponibles avec les packages parallel ou le duo doParallel + foreach. Attention à la loi d'Amdahl : le gain par cœur est décroissant.

Partie 3 : Forme du livrable

Au-delà de la qualité du code, la forme du livrable détermine la facilité de maintenance, de réutilisation et de communication des résultats. Choisir la bonne forme est une décision structurante.

  • R Markdown / Quarto — pour l'analyse et la présentation de résultats reproductibles
  • Paquet R — pour organiser, documenter et partager ses fonctions
  • Shiny — pour les outils interactifs d'aide à la décision

Choisir la bonne forme

R Markdown / Quarto

Format fusionnant syntaxe markdown et code R. Le fichier source et la version compilée (HTML, PDF) doivent tous deux être livrés : le .Rmd est la preuve de reproductibilité. Toujours nommer les chunks ; ne pas y déclarer de fonctions.

Paquet R

Rassembler ses fonctions dans un paquet résout les problèmes de dépendances non déclarées, d'absence de tests et de documentation non maintenue. Gestion fine des dépendances (Imports, Suggests), tests unitaires, documentation roxygen2 et vignettes.

Shiny

Transformer vos analyses en applications web réactives sans HTML/CSS/JS. Pour la production, utiliser golem qui impose une structure de paquet : tests, versionnage et déploiement sécurisé inclus.

Partie 4 : Sélection de paquets par cas d'usage

La force de R réside dans son immense bibliothèque de packages (plus de 20 000 sur le CRAN). Voici une sélection des incontournables classés par domaine.

1. Gestion de la data

  • dplyr — grammaire de la manipulation de données : filtrer, sélectionner, réorganiser, créer des variables, agréger, via des verbes simples et intuitifs. Très lisible avec le pipe |>.
  • tidyr — restructuration des données (format large ↔ long) pour que chaque variable soit une colonne et chaque observation une ligne. Indispensable avant modélisation ou visualisation.

2. Statistique et Machine Learning

  • caret — interface unifiée pour des centaines d'algorithmes. Gère tout le cycle de vie d'un modèle : prétraitement, sélection de variables, optimisation des hyperparamdètres, évaluation des performances.
  • tidymodels — version moderne et Tidyverse-compatible du ML. Collection de paquets (parsnip, recipes, rsample…) pour des pipelines de modélisation robustes et reproductibles. Plus modulaire que caret.

3. Graphique et Visualisation

  • ggplot2 — basé sur la « Grammaire des Graphiques ». Construction couche par couche. Qualité esthétique de standard professionnel (publication scientifique, presse).
  • plotly — transforme vos graphiques ggplot2 en versions interactives (zoom, survol, filtres) avec une seule fonction : plotly::ggplotly().
  • highcharter — interface R pour la bibliothèque JavaScript Highcharts. Graphiques dynamiques et élégants pour les tableaux de bord professionnels.

4. Shiny : Applications Web Interactives

  • shiny — framework de base. Programmation réactive : l'interface se met à jour instantanément à chaque interaction utilisateur. Idéal pour l'aide à la décision.
  • golem — impose une structure de paquet à votre application Shiny : tests unitaires, contrôle de version, déploiement sécurisé. Indispensable pour la production.

5. Débogage

  • base::browser() — insérée dans votre code, interrompt l'exécution et ouvre un environnement interactif. Vous pouvez inspecter les variables, exécuter le code ligne par ligne et identifier précisément l'origine d'une erreur. Outil de diagnostic primaire de tout développeur R.

Partie 3 : Forme du livrable

Au-delà de la propreté du code, la forme finale du livrable joue un rôle déterminant dans l'appréciation du client. Trois formes couvrent la quasi-totalité des cas d'usage :

  • R Markdown / Quarto — pour l'analyse et la présentation de résultats reproductibles.
  • Un paquet R — pour organiser, documenter, tester et partager ses fonctions.
  • Shiny — pour les outils interactifs d'aide à la décision.

Ces trois formes ne sont pas mutuellement exclusives : un paquet R peut être la fondation d'un R Markdown et d'une application Shiny à la fois.

Choisir la bonne forme de livrable

R Markdown / Quarto

Le format R Markdown (ou Quarto dans sa forme moderne) fusionne la syntaxe markdown avec du code R. Il est adapté pour la présentation de résultats ou la réalisation d'une analyse. Le fichier source et une version compilée (HTML, PDF…) doivent être tous deux fournis au client : le .Rmd est la preuve de la reproductibilité des résultats.

Bonnes pratiques :

  • Intégrer un minimum de code R dans les chunks — les fonctions ne doivent pas y être déclarées.
  • Toujours nommer les chunks pour se repérer dans le document.
  • Explorer les fonctions utiles de knitr : knitr::kable() pour afficher des tables, knitr::opts_chunk() pour définir globalement les paramètres des chunks.
  • Pour les rapports de présentation, utiliser echo=FALSE pour masquer le code et améliorer la lisibilité.

Un paquet R pour le code

Définir ses fonctions dans des scripts R isolés présente plusieurs inconvénients : dépendances non déclarées, absence de tests, documentation non maintenue. Rassembler ses fonctions dans un paquet résout ces problèmes. La création de paquets en R est relativement simple — référence : R Packages (2e) de Hadley Wickham & Jennifer Bryan.

Un paquet R permet de :

  • Gérer les dépendances avec Depends, Imports, Suggests et les tags @importFrom / @import de roxygen2.
  • Ajouter des tests unitaires en parallèle du développement (pas après). Le paquet codecov évalue la couverture du code — indicateur, non objectif.
  • Intégrer la documentation directement à chaque fonction, vérifiée lors du Check du paquet.
  • Lier des vignettes pour illustrer le fonctionnement des fonctions à l'utilisateur.
  • Intégrer des méta-données : auteur, licence, version…
  • Instaurer un versionnage avec suivi des corrections et des nouvelles fonctionnalités.

Shiny pour les outils interactifs

Shiny permet de transformer vos analyses R en applications web interactives sans HTML/CSS/JS. Il repose sur un modèle de programmation réactive : dès qu'un utilisateur modifie un paramètre, les calculs et les graphiques se mettent à jour instantanément.

Pour la production, golem est indispensable : il impose une structure de paquet à votre application, facilitant les tests unitaires, le contrôle de version et le déploiement sécurisé.

Partie 2 : Optimisation du code

L'optimisation est l'étape logique qui suit la réécriture d'un code propre. Elle a deux objectifs :

  • Mobiliser de manière efficiente les ressources (mémoire RAM et calcul processeur).
  • Diminuer le temps d'exécution du code.

En pratique, cela consiste à : utiliser les méthodes les plus adaptées à la volumétrie, minimiser le volume des tables, arbitrer entre deux processus similaires, et minimiser l'usage des boucles.

Remarque importante : l'optimisation ne doit pas se faire au détriment de la propreté. Le temps gagné côté utilisateur ne doit pas se transformer en temps perdu côté développeur.

Analyse des performances avec le benchmarking

L'outil de base est le benchmark : l'évaluation des performances d'un code ou d'une partie. Deux fonctions complémentaires sont couramment utilisées :

  • profvis::profvis() — s'exécute sur un code entier et analyse les performances de chaque étape. On identifie ainsi les goulots d'étranglement. En général, moins de 20 % du code est responsable de plus de 80 % du temps d'exécution (loi de Pareto).
  • microbenchmark::microbenchmark() — conçu pour analyser des blocs courts sur plusieurs itérations. Il fournit des indicateurs fiables pour comparer deux implémentations et mesurer l'évolution des gains avec l'augmentation du volume de données.

Les leviers d'optimisation

1. Affiner la lecture des inputs

Il faut éviter de stocker la totalité d'une table en mémoire. Filtrer les données et/ou sélectionner les colonnes dès la lecture sur le disque dur. Pour les fichiers Excel, utiliser les arguments col_names, skip et n_max. Pour une base de données SQL, optimiser la requête directement.

2. Gérer les données volumineuses avec data.table

Comparable à dplyr, le paquet data.table propose une syntaxe adaptée aux volumes importants. Dans ce contexte, son utilisation peut faire gagner un temps significatif : il minimise les copies en mémoire et exploite mieux le processeur que les approches classiques.

3. Vectoriser les processus itératifs

Une fonction vectorisée applique sa transformation simultanément à tous les éléments d'un vecteur, sans boucle for. Réaliser une opération par vectorisation est en général plus rapide et évite un niveau d'indentation supplémentaire.

  • base::Vectorize() — simule une vectorisation (wrapper de boucle, sans gain de vitesse, mais améliore la lisibilité).
  • base::rbind() — concaténations vectorisées.
  • plyr::join() — jointures performantes.
  • Famille base::apply (lapply, sapply, vapply…) — applications vectorisées sur listes et matrices.

4. Parallélisation

La parallélisation répartit l'exécution du code simultanément sur plusieurs unités de calcul (cœurs ou processeurs). Elle intervient après avoir optimisé le code lui-même. Deux questions à se poser :

  • Efficacité : comment maximiser l'utilisation des ressources disponibles ? Packages utiles : parallel, doParallel + foreach.
  • Efficience : la quantité de ressources mobilisées est-elle cohérente avec le besoin ? Le gain par cœur supplémentaire est décroissant (loi d'Amdahl) — identifier le nombre optimal de ressources avec les outils de benchmarking.

Attention : la parallélisation tend à complexifier le code et nécessite une certaine expérience pour être bien exploitée.

Partie 1 : Coder proprement en R

La notion de propreté est commune à tous les langages de programmation. Un code propre a les qualités suivantes : maintenabilité, imperfectibilité, clarté et limpidité.

« La logique doit être simple, pour que les bogues aient du mal à se cacher. Les dépendances doivent être minimes afin de faciliter la maintenance. La gestion des erreurs doit être totale. Les performances doivent être proches de l'idéal. Un code propre fait une chose et le fait bien. »
— B. Stroustrup, inventeur du C++

Les indicateurs de propreté convergent vers les critères suivants. Un code propre doit être :

  • Explicite : aucune règle n'est implicite, le lecteur n'a rien à deviner.
  • Lisible : les imbrications sont identifiées, le code est aéré, les noms sont pertinents.
  • Simple : le code est logique et va à l'essentiel.
  • Parcimonieux : aucune opération superflue n'est présente.
  • Non redondant : pas deux blocs/fonctions qui réalisent un traitement identique.
  • Harmonieux : le style est cohérent tout au long du script.

Le mythe de la reprise à zéro

Il est tentant de réécrire un code non propre depuis zéro, mais c'est généralement une mauvaise idée : les intentions du développeur d'origine ne sont pas claires et il manquera des informations cruciales. À la place, appliquez ces deux règles :

  • Quand vous travaillez sur un code, laissez-le toujours un peu plus propre qu'il ne l'était.
  • « Plus tard signifie jamais » : si vous voyez un moyen évident d'améliorer un code, faites-le maintenant.

Les règles de propreté en R

1. Respecter les conventions d'indentation

En R, l'indentation n'a pas de conséquences sur l'exécution. Néanmoins, un script mal indenté perd significativement en lisibilité. Une bonne indentation indique aussi quelles parties du code sont particulièrement imbriquées — et donc lesquelles pourraient bénéficier d'une réécriture.

2. Écrire des commentaires uniquement s'ils sont irremplaçables

Les commentaires sont souvent utilisés pour compenser des défauts réels du code. Si le code est propre, un développeur n'a pas besoin de commentaires pour le comprendre. Le bon commentaire est celui qui ne peut pas être remplacé par du code plus explicite.

3. Utiliser le pipe natif |>

Le pipe permet de construire un pipeline pour appliquer une suite de transformations à un input, sans créer de variables intermédiaires. Préférer le pipe natif |> au %>% de magrittr : il est légèrement plus rapide et évite une dépendance supplémentaire.

4. Identifier, minimiser et mettre à jour les paquets importés

Les importations complexifient la maintenance et le déploiement. Signaler les fonctions importées avec la syntaxe paquet::methode pour identifier les dépendances superflues. Pour les paquets dont seule une ou deux fonctions sont utilisées, chercher des alternatives natives avant de les conserver.

5. Gérer explicitement les erreurs de lecture/écriture

Utiliser base::file.exists() ou base::dir.exists() avant toute lecture pour détecter rapidement les fichiers manquants. Construire les chemins avec base::file.path() — chaque répertoire correspond à un argument, ce qui améliore la lisibilité et la portabilité.

6. Pas de codage dynamique

Ne jamais utiliser eval(), parse(), get() ou assign(). Ces fonctions rendent le débogage laborieux. Si vous les trouvez dans un script existant, évitez de le modifier. Dans 99 % des cas, ils ne sont pas nécessaires.

7. Ne pas utiliser $ pour référencer les colonnes

Avec les data.frames, il existe deux façons d'accéder à une colonne : Table[["colonne"]] ou Table$colonne. Préférer les crochets : l'opérateur $ fait de l'auto-complétion implicite et peut silencieusement retourner une colonne inattendue si le nom n'existe pas exactement.

Gestion des fonctions

Règle 1 — Une fonction ne fait qu'une seule chose, et le fait bien

Cette règle implique que :

  • Le nom de la fonction énonce clairement ce qu'elle est censée faire.
  • Le vocabulaire est cohérent avec le niveau d'abstraction : métier pour les fonctions de haut niveau, technique pour les fonctions de bas niveau.
  • Pas d'effets de bord — la fonction ne produit que l'effet qu'elle est censée produire.
  • Pas d'arguments indicateurs (booléens qui changeraient le rôle de la fonction) : si vous en avez un, vous avez besoin de deux fonctions distinctes.
  • Des tests unitaires vérifient que la fonction remplit son objectif, y compris dans les cas particuliers.

Règle 2 — Écrire des fonctions courtes

Le seuil maximal usuel varie de 30 à 50 lignes dans la littérature, mais peut descendre jusqu'à 10. Plutôt que de fixer un seuil arbitraire : à chaque passe d'écriture, considérez que la fonction est trop longue et essayez de la raccourcir.

Règle 3 — Limiter drastiquement le nombre d'arguments (idéalement ≤ 3)

Chaque argument supplémentaire complexifie l'utilisation et nécessite des tests unitaires dédiés. Pour s'approcher de ce seuil :

  • Paramètres techniques constants : ne pas les mettre en argument. S'ils ne varient pas, ce sont des variables locales.
  • Utiliser des listes : elles remplacent souvent la POO en R. Passer une liste en argument est acceptable si sa structure est clairement définie.
  • Paramètres utilisateur : les récupérer via une fonction dédiée depuis un fichier de configuration isolé (projet R) ou un objet global (paquet R).

L'écriture de fonctions est un processus itératif. La première version n'est jamais la version finale.

Introduction : les bonnes pratiques R

On appelle bonnes pratiques tout ce qui garantit que le produit final soit de bonne qualité. La qualité est tout ce qui entoure le produit final au-delà de son simple bon fonctionnement. En informatique, un code fonctionnel n'est pas nécessairement un code de qualité.

Dans le cadre de R, ces bonnes pratiques sont d'autant plus importantes qu'elles pourraient vous aider à publier des paquets sur le CRAN (dépôt officiel de R), et donc contribuer au modèle open-source de ce langage.

  • L'optimisation de l'exécution — benchmarking, vectorisation, parallélisation

Qu'est-ce qu'un code de qualité ?

Un code propre, quel que soit son langage, présente les qualités suivantes :

  • Maintenabilité : il peut être lu et amélioré par un développeur autre que son auteur.
  • Imperfectibilité : rien ne permet de l'améliorer de manière évidente.
  • Clarté : il demande peu d'effort pour être lu et compris.
  • Limpidité : il retranscrit parfaitement l'idée d'origine du développeur.
